# Directive 08: KPI Calculation Uncertainty (STORY-007)

## Goal

Prove — explicitly, against the literal acceptance criteria — that the
system stops and asks for clarification when a KPI calculation is
genuinely uncertain, and that every KPI's evidence level (including `low`)
is shown and logged. Close the one gap found: nothing anywhere exercises
the `low` evidence level end to end.

Satisfies REQ-008 (FUNC, must) — "stop and ask for clarification when
unsure" — and REQ-009 (FUNC, must) — "assign an evidence level to each
KPI: high, medium, or low confidence."

## Confirmed with the project owner before building (2026-09-19)

This is not a build-from-scratch story. Both requirements are already
substantially implemented, from prior sessions, without ever being labeled
STORY-007:

- `backend/src/services/kpiService.ts` (STORY-002) already assigns every
  `Kpi` an `evidenceLevel` from coverage-based thresholds
  (`KPI_HIGH_EVIDENCE_MIN` / `KPI_MEDIUM_EVIDENCE_MIN`), boundary-tested at
  `kpiService.test.ts:175`; already returns `clarificationsNeeded[]` with a
  plain-English `question` instead of fabricating a number when genuinely
  unsure (a test there already cites "REQ-008 / STORY-007" in a comment);
  already logs per-KPI evidence levels and clarification codes on every
  calculation (`logKpiCalculation`).
- `frontend/src/components/KpiCard.tsx` and `frontend/src/pages/Dashboard.tsx`
  (STORY-003) already render the evidence-level badge on every KPI card and
  a "Before these numbers are final" section listing clarification
  questions.

**The one real gap:** the boundary test only exercises `high` and
`medium`; `Dashboard.test.tsx` only asserts `"High confidence"` renders;
there is no `KpiCard.test.tsx` at all. `low` has never been proven to
actually happen or actually display, even though the mechanism is generic
across all three levels. This directive's job is to close that gap and
verify the rest with tests framed around STORY-007's own acceptance
wording, not to rebuild working mechanism a second time.

## Mapping to acceptance criteria

1. **"...the system requests clarification"** — already true
   (`clarificationsNeeded[]` end to end: `calculateKpis` → upload response
   → dashboard response → the "Before these numbers are final" section).
   Verified, not rebuilt.
2. **"...a KPI with low confidence, when displayed, then it shows the
   evidence level"** — mechanism already generic across all three levels;
   `low` specifically was never exercised. **This is what this story
   builds** — the missing test coverage, at both layers.
3. **"...logs all uncertainty handling and evidence levels"** — already
   true (`logKpiCalculation`'s `evidence`/`clarificationCodes`,
   `logDashboardAccess`'s `clarificationCount`). Verified, not rebuilt.

## Failure paths (mapped to what already handles them)

- **Clarification request not sent** — the plumbing is a single typed
  path (`KpiCalculation.clarificationsNeeded` flows unchanged through
  `uploadRoute.ts` and `dashboardRoute.ts`, contract-guarded by
  `AssertMutual`/`AssertAssignable` in both `uploadContract.ts` and
  `dashboardContract.ts`) — there's no separate "send" step to fail
  silently; if it's on the `KpiCalculation`, it reaches the response.
- **Incorrect evidence level** — the boundary test, now including `low`,
  is the guard against a threshold regression.
- **User confusion** — `clarificationsNeeded[].question` is always a full
  English sentence generated by the calculation code (see the synonym/
  coverage logic in `kpiService.ts`), never a raw error code or column
  name alone; the UI renders `question` directly, never `code`.

## Guardrails not otherwise addressed above

- "Maintain a record of insights and allow users to undo changes" — not
  applicable to evidence-level display itself; belongs to STORY-014.
- "Verify significant drops or increases in KPIs before sending alerts" —
  already built, separately, in STORY-012's approval-hold work
  (`directives/05-alerts.md`).
- "Ensure data accuracy and integrity throughout the process" — this is
  what the clarification mechanism *is*: refusing to present a number the
  data doesn't support, rather than rounding up. Already the core of
  `calculateKpis`.
